## Phase Goal

**As a** Colombo consumer, **I want to** browse a real, structured directory of local
businesses — with categories, hours, address, attributes, and photos — **so that** I can
find and learn about a business before visiting or contacting it.

<objective>
Stand up the full Next.js + Prisma + Postgres/PostGIS stack from an empty repository and
prove it end-to-end: a visitor can open the directory index, see real seeded businesses,
click into one, and see its core LIST-01 fields (name, categories, description,
district/free-text address, lat/lng) rendered with an accurate map pin. Web-only via
Next.js is the platform surface per CONTEXT.md D-01 (React Native mobile is explicitly
deferred past Phase 1). This is the Walking Skeleton for the whole project — every later
phase (and every other plan in this phase) builds on the architectural decisions made here
without renegotiating them (see `SKELETON.md`).

Purpose: prove the full stack is wired before building out every LIST-02..06/LOC-02 detail
on top of it, and establish the root-level (no `src/`) directory layout, Prisma schema
shape, and presentational/route-component split that plans 01-02..01-04 extend.

Output: a running Next.js app backed by a local Postgres+PostGIS database, seeded with a
small real Colombo dataset, with a working directory→business-page click-through.
</objective>

Prisma schema shape (prisma/schema.prisma) — all four models needed for the WHOLE phase are
defined in this one migration so later plans only ever ADD fields/UI, never re-migrate a
missing table:

```prisma
model Business {
  id                  String    @id @default(cuid())
  slug                String    @unique
  name                String
  description         String
  primaryCategories   String[]
  secondaryCategories String[] @default([])
  district            String
  addressFreeText     String
  latitude            Float
  longitude           Float
  location            Unsupported("geography(Point,4326)")?
  attributes          Json      @default("{}")
  createdAt           DateTime  @default(now())
  updatedAt           DateTime  @updatedAt
  hours               BusinessHours[]
  hoursOverrides      BusinessHoursOverride[]
  photos              BusinessPhoto[]

  @@index([district])
}

model BusinessHours {
  id              String   @id @default(cuid())
  businessId      String
  business        Business @relation(fields: [businessId], references: [id], onDelete: Cascade)
  dayOfWeek       Int
  openTime        String
  closeTime       String
  crossesMidnight Boolean  @default(false)

  @@index([businessId, dayOfWeek])
}

model BusinessHoursOverride {
  id              String   @id @default(cuid())
  businessId      String
  business        Business @relation(fields: [businessId], references: [id], onDelete: Cascade)
  date            DateTime @db.Date
  isClosed        Boolean  @default(true)
  openTime        String?
  closeTime       String?
  crossesMidnight Boolean  @default(false)

  @@unique([businessId, date])
}

model BusinessPhoto {
  id          String   @id @default(cuid())
  businessId  String
  business    Business @relation(fields: [businessId], references: [id], onDelete: Cascade)
  url         String
  caption     String?
  sortOrder   Int      @default(0)
  isMenuPhoto Boolean  @default(false)
  createdAt   DateTime @default(now())

  @@index([businessId])
}
```

Migration also adds (raw SQL, in the same or a follow-up migration file — see RESEARCH.md
Pattern 1 for the exact trigger): a GiST index on `location`, and a
`BEFORE INSERT OR UPDATE OF latitude, longitude` trigger that sets
`location = ST_SetSRID(ST_MakePoint(longitude, latitude), 4326)::geography`. This is static
DDL committed to a migration file — never string-built from request/user input.

Shared TypeScript types (lib/types/business.ts) that all later plans import instead of
redefining:

```typescript
export interface BusinessHoursRow {
  dayOfWeek: number;
  openTime: string;
  closeTime: string;
  crossesMidnight: boolean;
}
export interface BusinessHoursOverrideRow {
  date: string; // "yyyy-MM-dd"
  isClosed: boolean;
  openTime: string | null;
  closeTime: string | null;
  crossesMidnight: boolean;
}
export interface BusinessPhotoRow {
  id: string;
  url: string;
  caption: string | null;
  sortOrder: number;
  isMenuPhoto: boolean;
}
export interface BusinessDetail {
  id: string;
  slug: string;
  name: string;
  description: string;
  primaryCategories: string[];
  secondaryCategories: string[];
  district: string;
  addressFreeText: string;
  latitude: number;
  longitude: number;
  attributes: Record<string, unknown>;
  hours: BusinessHoursRow[];
  hoursOverrides: BusinessHoursOverrideRow[];
  photos: BusinessPhotoRow[];
}
```

`components/business/business-page.tsx` exports `BusinessPageView(props: { business:
BusinessDetail; openNow: boolean | null })` — a presentational component (no Prisma import,
no `"use client"` needed for the parts built in this plan). `openNow` is `null` in this plan
(computed for real starting in 01-02) and the component must render nothing for a `null`
value (no badge) — 01-02 will pass a real boolean and add the badge. Plan 01-02 edits this
file to add an hours section; 01-03 edits it again to add attributes/gallery/menu sections —
both are expected, sequential edits to the same file (hence 01-02 and 01-03 run in later,
sequential waves, not parallel with each other).

## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| Developer (seed-data.json author) -> Postgres | The seed script is the only write path in Phase 1; input is developer-curated, not end-user-supplied, but is still validated as if untrusted since the file will be hand-edited iteratively |
| Browser -> Next.js Server Component | All Phase 1 reads are public/unauthenticated by design (no login exists yet) |
| Browser -> OpenStreetMap tile CDN | Leaflet fetches map tiles directly from the browser, never proxied through the Next.js server |

## STRIDE Threat Register

| Threat ID | Category | Component | Severity | Disposition | Mitigation Plan |
|-----------|----------|-----------|----------|-------------|-----------------|
| T-01-01 | Tampering | PostGIS geography-sync trigger (raw SQL in migration) | medium | mitigate | Trigger SQL is static DDL committed to a versioned migration file, never string-built from request/user input; no `$queryRawUnsafe` used anywhere in this plan |
| T-01-02 | Tampering | `prisma/seed.ts` writing to `businesses.attributes` jsonb column | high | mitigate | `businessSeedSchema.parse()` (Zod, `.strict()`) runs on every record before any `upsert` call — malformed/oversized payloads throw before reaching the DB |
| T-01-03 | Information Disclosure | `app/business/[slug]/not-found.tsx` / server error paths | medium | mitigate | Use Next.js's `notFound()` + a custom `not-found.tsx` with static copy; no Prisma error object or stack trace is ever passed into rendered output |
| T-01-04 | Information Disclosure | All business data readable with no auth | low | accept | By design — Phase 1 has no accounts (AUTH-01..03 are Phase 2) and all seeded listings are intentionally public per LIST-01 |
| T-01-SC | Tampering | npm package supply chain (`next`, `react`, `prisma`, `zod`, `tsx`, etc.) | high | accept | 01-RESEARCH.md's Package Legitimacy Audit already vetted every package in this plan's install list — all "Approved", zero `[SLOP]`, `[SUS]` flags were recency-artifacts only (each has an official org repo and 10M+ weekly downloads) — audit explicitly concludes no `checkpoint:human-verify` is warranted; `postgis/postgis` is the official PostGIS-project Docker Hub image |
