## Phase Goal

**As a** Colombo consumer, **I want to** search, filter, and browse the business directory entirely as a guest, signing up via phone OTP only when I'm ready, **so that** I can quickly decide where to eat, shop, or hire a local service without friction or a forced login.

<objective>
Build the user-facing phone-OTP login flow (phone entry -> OTP entry -> optional name prompt) that calls 02-03's already-working backend endpoints.

Purpose: This is where AUTH-01 becomes something a real user can click through, and where AUTH-03's "progressive profile" (phone-only signup, name is optional and asked for later, never blocking) becomes concrete UI. Runs in parallel with 02-04 (Search Results) and 02-06 (Header) since none share files.
Output: `/login` page with a working two-step flow; a non-blocking post-verification name prompt that never reappears once dismissed.
</objective>

```

POST /api/auth/otp/verify body: { phone: string; code: string } -> { ok: true, user: { id, name: string | null, hasSeenProfilePrompt: boolean } } | 400 { error: string }
```
A successful verify call sets a sealed httpOnly session cookie automatically (`Set-Cookie`) — the client never reads or stores a token itself, only relies on the browser's normal cookie handling for subsequent requests.

<threat_model>
## Trust Boundaries

| Boundary | Description |
|----------|--------------|
| Browser form input → `/api/auth/otp/send`, `/verify`, `/profile` | Client-side validation is a UX convenience only; every field is independently re-validated server-side (already true of 02-03's routes; `/profile` adds its own `.strict()` schema here) |
| `/api/auth/profile` → session | Requires an existing session (`userId`); cannot be called by an anonymous guest to modify an arbitrary user's name |

## STRIDE Threat Register

| Threat ID | Category | Component | Severity | Disposition | Mitigation Plan |
|-----------|----------|-----------|----------|-------------|-----------------|
| T-02-07 (reuse) | Information Disclosure | OTP-entry dev-mode caption | high | mitigate | The caption renders only when the send response actually included a `devCode` field, which 02-03 already gates behind `NODE_ENV !== "production"` server-side; this plan adds no separate client-side environment check that could drift out of sync with the server's gate. |
| T-02-12 | Elevation of Privilege | `/api/auth/profile` | medium | mitigate | The route reads `userId` exclusively from the server-verified, sealed session cookie (never from a client-supplied body field) before deciding which `User` row to update — a caller can only ever update their own row. |
</threat_model>
