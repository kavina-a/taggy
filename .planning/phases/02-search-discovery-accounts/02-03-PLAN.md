## Phase Goal

**As a** Colombo consumer, **I want to** search, filter, and browse the business directory entirely as a guest, signing up via phone OTP only when I'm ready, **so that** I can quickly decide where to eat, shop, or hire a local service without friction or a forced login.

<objective>
Implement the complete phone-OTP round trip — send (rate-limited, dev-stub transport) and verify (hash compare, attempt lockout, session issuance) — as backend logic with no UI yet.

Purpose: This is the backend half of AUTH-01, built and tested in isolation from the login page/forms (02-05) so its security-critical logic (rate limiting, timing-safe comparison, session sealing) gets full-context TDD attention. It runs in parallel with 02-02's Search Engine Core since neither touches the other's files.
Output: `POST /api/auth/otp/send` and `POST /api/auth/otp/verify` fully functional against the local dev database, a reusable `getSession()` helper, and a documented-limitation in-memory rate limiter.
</objective>

## Trust Boundaries

| Boundary | Description |
|----------|--------------|
| Anonymous client → `/api/auth/otp/send` | Fully unauthenticated endpoint accepting a phone number |
| Anonymous client → `/api/auth/otp/verify` | Fully unauthenticated endpoint accepting a phone + 6-digit code, capable of minting a session |
| `getSession()` cookie ↔ browser | The only place session state crosses the network as a cookie |

## STRIDE Threat Register

| Threat ID | Category | Component | Severity | Disposition | Mitigation Plan |
|-----------|----------|-----------|----------|-------------|-----------------|
| T-02-02 | Spoofing | `/api/auth/otp/verify` (OTP brute-force) | high | mitigate | `MAX_OTP_ATTEMPTS = 5` lockout per challenge row plus the 5-minute `OTP_EXPIRY_MS` (from 02-01) together bound the brute-force window to well under the 1,000,000-code keyspace; `verifyOtpCode` uses `timingSafeEqual`, never `===`. |
| T-02-03 | Denial of Service | `/api/auth/otp/send` (SMS/send-flooding) | medium | mitigate | Per-phone (3/min) AND per-IP (10/min) rate limits via `checkRateLimit`, enforced before any `OtpChallenge` row is created or `transport.send` is called. |
| T-02-04 | Tampering | Session cookie (`lib/session.ts`) | high | mitigate | `iron-session`'s sealed (encrypted + integrity-checked) cookie; `httpOnly: true` always, `secure: true` in production, `sameSite: "lax"`. A tampered cookie fails to decrypt rather than decoding into attacker-controlled session data. |
| T-02-05 | Information Disclosure | `/api/auth/otp/send` response shape/timing | medium | mitigate | The send route never queries or branches on `User` existence; response shape and (to the extent Node's async scheduling allows) code path are identical for a new vs. already-registered phone. The `User` row is created only in the verify route, after successful code entry. |
| T-02-06 | Tampering | `OtpChallenge.codeHash` | high | mitigate | Inherited from 02-01's `hashOtpCode` — codes are HMAC-hashed before this plan's `create` call ever writes a row. |
| T-02-07 | Information Disclosure | `devCode` field in the send response | high | mitigate | Strictly gated behind `process.env.NODE_ENV !== "production"`; a production build (`NODE_ENV=production`, Next.js's own default for `next build`/`next start`) never includes this field in the response body. |
</threat_model>
