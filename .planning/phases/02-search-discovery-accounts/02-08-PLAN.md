## Trust Boundaries

| Boundary | Description |
|----------|--------------|
| Filter/sort URL params → `/search`, `/api/search` | Same untrusted-input boundary as 02-04; every new param flows through `parseSearchParams`'s `.strict()` schema before reaching `runSearchQuery` |

## STRIDE Threat Register

| Threat ID | Category | Component | Severity | Disposition | Mitigation Plan |
|-----------|----------|-----------|----------|-------------|-----------------|
| T-02-01 (reuse) | Tampering | Filter param composition into `SearchFilters` | high | mitigate | This plan only ever forwards `parseSearchParams`'s already-validated, typed fields into `runSearchQuery`'s `SearchFilters` object; it never constructs SQL and never bypasses 02-02's parameterized-query boundary. |
| T-02-14 | Denial of Service | Debounced live-filter fetch to `/api/search` | low | accept | The 300ms debounce plus the existing fixed page size and query-length caps (T-02-08, 02-04) bound the request rate a single client can generate through rapid filter interaction; acceptable at current traffic/data volume. |
</threat_model>
