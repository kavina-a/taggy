# Phase 2 — UI Design Contract

> Visual and interaction contract for frontend phases. Generated by gsd-ui-researcher, verified by gsd-ui-checker.

**Scope note:** This phase EXTENDS Phase 1's locked design system (see
`.planning/phases/01-business-directory-foundation/01-UI-SPEC.md`) rather than replacing it.
Every token below (spacing, typography, color) is identical to Phase 1 unless explicitly
called out as new. Screens in scope: search results page, home/discovery page, phone-OTP
auth flow (phone entry → OTP entry → minimal name prompt), and header updates (login state +
language switcher). Do NOT design: reviews, ratings input, Q&A, photo upload, collections,
business claim, or owner-response UI — all are later phases (3-5).

## Spacing Scale

Unchanged from Phase 1 — reuse the same 8-point scale:

| Token | Value | Usage |
|-------|-------|-------|
| xs | 4px | Icon gaps, chip inline padding (filter chip icon-to-label, sort dropdown icon) |
| sm | 8px | Compact spacing (filter row internal gap, OTP digit box gap) |
| md | 16px | Default spacing (search result card padding, form field gaps, rail card gap) |
| lg | 24px | Section padding (between search header/filter bar and results grid; between rail sections on home page) |
| xl | 32px | Layout gaps (page gutters tablet+, sidebar-to-results gap on desktop search) |
| 2xl | 48px | Major section breaks (between home page hero/search bar and first rail) |
| 3xl | 64px | Page-level vertical rhythm on desktop |

Exceptions (extends Phase 1's 44px rule with two new cases):
- **44px minimum tap target** on all interactive elements — unchanged rule, now also applies
  to: filter drawer trigger button, sort dropdown trigger, each OTP digit box, "Send code" /
  "Verify" CTAs, header login/avatar control, category shortcut tiles, rail horizontal-scroll
  cards (whole card tappable).
- **OTP digit boxes:** each box is a fixed 44x44px minimum square (not just min-height) since
  it's tapped individually — pad with the `input-otp` component's built-in slot sizing, do not
  shrink below 44px even on narrow (320px) viewports; use horizontal scroll or reduced
  inter-box gap (down to 4px `xs`) before shrinking box size.
- **Filter sheet handle/drag area:** the sheet's drag handle (mobile bottom-sheet) needs a
  generous invisible hit area (min 44px tall strip) even though the visible handle graphic is
  smaller, consistent with the existing "pad to 44px with transparent hit-area" principle.

## Typography

Unchanged scale from Phase 1 — same 4 sizes, 2 weights, no additions:

| Role | Size | Weight | Line Height |
|------|------|--------|-------------|
| Label | 14px | 400 (regular) | 1.5 |
| Body | 16px | 400 (regular) | 1.5 |
| Heading | 20px | 600 (semibold) | 1.2 |
| Display | 28px | 600 (semibold) | 1.2 |

New usage mapping for Phase 2 elements (executor must not invent new sizes/weights):
- **Display (28/600):** Home/discovery page title ("Find it in Colombo" or equivalent hero
  headline); OTP digit characters themselves (large, legible on mobile).
- **Heading (20/600):** Rail section titles ("Trending Near You", "Top Rated", "New
  Businesses", "Browse by Category"); search results page count line is NOT this size (see
  Body below); auth screen headings ("Log in or sign up", "Enter the code", "What should we
  call you?"); filter sheet/sidebar title ("Filters").
- **Body (16/400):** Search bar input text, phone number input text, result count summary
  ("128 results near you"), business card snippet text, filter option labels when they need
  more prominence (category names in filter list), name-prompt input text.
- **Label (14/400):** Filter chip text (price tier, "Open now"), sort dropdown current-value
  text, distance slider value readout ("Within 5 km"), business card metadata row (price
  tier · distance · category), rating/review-count text, breadcrumb text, language switcher
  current value, OTP helper text ("Sent to +94 7X XXX XXXX"), resend-code link text.

## Color

Unchanged base palette from Phase 1 — reuse the existing tokens exactly (already implemented
in `app/globals.css` as `--brand-accent: #ea580c`, `--status-open`, `--status-closed`):

| Role | Value | Usage |
|------|-------|-------|
| Dominant (60%) | `#FFFFFF` (white) | Page background — search results page, home page, auth screens |
| Secondary (30%) | `#F4F4F5` (neutral-100, shadcn `--secondary`) | Result cards, filter sidebar/sheet background, rail card background, OTP digit box background (unfilled state) |
| Accent (10%) | `#EA580C` (`--brand-accent`, orange-600) | Reserved ONLY for: search bar submit button, header "Log in" CTA button (guest state), "Send code" / "Verify" primary CTAs on auth screens, active sort-option checkmark, active/selected filter chip fill (e.g. selected price tier or category chip), active rail-nav pagination dot (if used) |
| Destructive | `#DC2626` (red-600, shadcn `--destructive`) | Not used in this phase's happy path — no delete/report/destructive action exists yet (reviews/reporting arrive Phase 3-4). Token exists for consistency only. |

Existing semantic tokens (outside the 10% accent budget, reused as-is):

| Role | Value | Usage |
|------|-------|-------|
| Status — Open | `#16A34A` (`--status-open`) | "Open now" badge on search result cards and rail cards |
| Status — Closed | `#71717A` (`--status-closed`, neutral, not red) | "Closed" badge — same non-alarming neutral treatment as Phase 1 |

**Accent reserved for (explicit list — nothing else may use `--brand-accent`):** search
submit button, header guest "Log in" CTA, auth-screen primary CTAs ("Send code"/"Verify"/
"Save" on name prompt), active sort-option indicator, selected filter chip fill. Never use
accent for: rail titles, category shortcut tiles (use secondary/neutral with an icon — accent
would visually compete with the real CTAs above), map pins (keep map pins in the existing
neutral/status-open palette already used in `business-map.tsx`, not accent-orange, so pins
don't visually compete with the one true accent CTA per screen), or the OTP digit boxes'
filled state (use `--foreground`/neutral fill with a subtle `--ring` focus outline, not
accent — accent stays reserved for the actual submit action).

**Logged-in header state:** avatar/name text uses `--foreground` (plain neutral text), not
accent — only the action of logging in (while a guest) is accent-colored; being logged in is
not itself a call-to-action.

## Screens In Scope

### 1. Search results page (`/search`)
- **Layout:** Mobile — single column: search bar (sticky top) → filter/sort trigger row →
  result cards stacked → map accessible via a "Map" toggle button (full-screen sheet/overlay,
  not a permanently split view, to preserve scroll real estate on small screens). Desktop
  (≥1024px) — search bar full width top, then a two-column body: left column results list
  (scrollable, ~55-60% width), right column a sticky map with pins (~40-45% width),
  reusing `components/business/business-map.tsx`. Filters render as an inline left-of-results
  sidebar on desktop, a bottom `sheet` drawer on mobile (D-08 — non-negotiable, already
  decided).
- **Result card:** extends `components/directory/business-card.tsx` — add price tier badge
  (`$`/`$$`/`$$$`/`$$$$`, Label-sized, neutral/secondary background — not accent), rating +
  review count (or "No reviews yet" per copy contract above), distance ("1.2 km"), a one-line
  snippet (business description truncated), and the existing Open/Closed status badge. Do not
  build a second, parallel card component — extend the existing one with optional props so
  Phase 1's directory index keeps working unchanged.
- **Filter contents:** category (checkbox list, sourced from `lib/categories/category-config.ts`
  — do not hardcode a duplicate list), price tier ($/$$/$$$/$$$$ multi-select chips), "Open
  now" (single checkbox), distance radius (slider, discrete stops at 1/3/5/10/25 km), rating
  threshold (chip row: "Any", "3+", "4+", "4.5+"), category-conditional attributes (checkboxes,
  shown only when a relevant category is active — reuse the attribute schema keys from
  `category-config.ts`, same source of truth as `attribute-badges.tsx`).
- **Sort control:** `dropdown-menu` with exactly the 4 options from SRCH-04, "Recommended"
  pre-selected by default, positioned top-right of the results list header row (desktop) or
  inline next to the filter trigger (mobile).
- **Focal point:** the results list is the focal point on mobile (map is opt-in via toggle);
  on desktop the results list remains primary with the map as a supporting, always-visible
  companion — never let the map dominate more than ~45% of viewport width.

### 2. Home / discovery page (`/`)
- **Layout:** Hero section (Display headline + search bar, centered, generous 2xl/3xl vertical
  spacing) → horizontally-scrollable rails in this order: Trending Near You → Top Rated → New
  Businesses → Browse by Category (this last one is a grid of category shortcut tiles, not a
  horizontal scroll — icon + label, reusing lucide icons already mapped per category, tappable
  straight into a pre-filtered `/search?category=...`).
- **Rail cards:** a condensed variant of the search result card — photo, name, one metadata
  line (category · price tier or distance, whichever is more relevant to that rail's context),
  Open/Closed badge. Omit the snippet text in rail cards to keep them compact enough for
  horizontal scroll (roughly card width 240-280px on mobile).
- **Rail data honesty:** per CONTEXT.md's Claude's Discretion note, rail contents are simple
  heuristics (recently added, stable random sample) since no telemetry exists — the UI itself
  must not imply real personalization or trending signal it doesn't have (no "🔥 12 people
  viewed this today" style copy anywhere this phase).

### 3. Auth flow (`/login` or equivalent route)
- **Step 1 — Phone entry:** heading, body copy, phone `input` (with `label`), "Send code"
  primary CTA (accent), routes to Step 2 on submit.
- **Step 2 — OTP entry:** heading, body copy showing the phone number just entered, 6-digit
  `input-otp` (grouped 3+3 with a visual gap, per the standard shadcn OTP pattern), "Verify"
  primary CTA (accent, disabled until 6 digits entered), "Resend code" link with cooldown
  timer, inline error copy on wrong code (see Copywriting Contract).
- **Step 3 — Progressive profile prompt (`dialog`, non-blocking):** shown once, immediately
  after first successful verification, as a dismissible dialog over the page the user was
  trying to reach (not a route of its own) — "Save" or "Skip for now" both return the user to
  where they came from. Never re-shown on subsequent logins once dismissed/completed.
- **Guest-first framing:** nothing in this flow is reachable except via the header "Log in"
  CTA — no page in the app auto-redirects to `/login` or blocks rendering behind an auth check
  in this phase (D-05).

### 4. Header (global, `app/layout.tsx`)
- Adds, left-to-right on desktop (right-to-left stacking priority on mobile — collapse into
  an overflow/hamburger only if space genuinely runs out; login state and language switcher
  should stay visible before anything gets hidden): existing logo/nav (Phase 1) → language
  `select` → login CTA / logged-in avatar+dropdown.
- Language switcher and login state must both remain visible and reachable from every screen
  in this phase's scope (search, home, business page, auth screens).

## Mobile & Performance Notes

Extends Phase 1's non-negotiables (same target audience: Sri Lankan consumers, 3G/4G,
lower-end Android, often outside Colombo):

- **Mobile-first responsive layout** for all four screens above — build single-column mobile
  first, then expand to the desktop split-column search layout.
- **Filter sheet performance:** filter changes should not require a full page reload on
  mobile where avoidable — prefer client-side query-param updates with a debounced fetch
  (Route Handler under `app/api/` per CONTEXT.md's Integration Points note), since the
  existing Server-Component-only pattern (Phase 1) would otherwise reload the whole page on
  every filter tap.
- **Map toggle, not permanent split, on mobile** — loading a live Leaflet map alongside a full
  result list on a slow connection is wasteful; keep the map lazy/on-demand via the existing
  `business-map-dynamic.tsx` dynamic-import pattern.
- **OTP screen must work without JS-heavy autofill assumptions** — support native SMS
  autofill (`autocomplete="one-time-code"` on the underlying input) since the target audience
  is exactly the kind of user who benefits most from not hand-typing a 6-digit code twice.
- **44px minimum tap targets** everywhere (see Spacing Scale exceptions above) — this now
  includes OTP digit boxes and filter chips specifically, both new categories of small
  interactive controls this phase introduces.
