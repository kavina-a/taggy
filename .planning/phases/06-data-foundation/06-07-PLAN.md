<objective>
Generate 5-60 realistic reviews per business (skewed 3-5 star distribution, 3-year date spread,
80-400 word bodies composed from a large sentence-fragment pool, some carrying 1-3 local review
photos), back every review's Useful/Funny/Cool counts with real ReviewVote rows, and tag every
seeded BusinessPhoto with a PhotoTag value — then wire all of it into `prisma/seed.ts` so
`Business.avgRating`/`reviewCount` recompute from real content.

Purpose: This is the phase's centerpiece content-generation slice — the "realistic" review corpus
every later Yelp-parity page (Phase 8/9) renders against, and the last plan in the dependency
chain since it needs 06-04's real seeded users and 06-05's real local image pool to exist first.
Output: A real `prisma db seed` run produces a full, realistic, internally-consistent review
corpus with real vote-backed counts and tagged photos.
</objective>

| T-06-16 | Tampering (data-integrity) | prisma/seed-data/generators/generate-reviews.ts | medium | mitigate | Generated review text is validated through the same `createReviewSchema` bounds the live `POST /api/reviews` route enforces (min 50 / max 5000 chars) — seed data can never ship content that would fail the platform's own real validation, and every seeded review is explicitly `visibilityStatus: "recommended"` by construction rather than routed through REV-03's live spam filter (which would otherwise flag near-duplicate template output as `not_recommended`, contradicting DATA-06's "realistic" goal) |
| T-06-17 | Repudiation | prisma/seed.ts vote-count recompute | low | accept | `usefulCount`/`funnyCount`/`coolCount` are set from real `ReviewVote` rows every seed run (never independently of them), matching the Phase 4 decision that these denormalized fields must always be derivable from real vote rows — no drift risk specific to seed data |
| T-06-18 | Tampering (accidental content loss) | prisma/seed.ts `review.deleteMany` | low | accept | Scoped to `businessId: upserted.id` only, inside the same transaction as that business's own upsert — cannot affect any other business's reviews, and only fires for businesses present in `businesses.json` (the same idempotent-reseed contract every other relation in this file already follows) |
